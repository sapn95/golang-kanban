# 0003 — Coarse-grained store interface and portable IDs

Status: proposed
Date: 2026-09-05

## Context

Phase 1 puts four backends behind one interface: SQLite, Postgres, MongoDB,
and S3 (one JSON object per board with ETag-based optimistic locking). The
interface has to be designed for the weakest of them:

- S3 has no transactions and no partial updates: every write is
  read-modify-write of a whole board.
- MongoDB has single-document atomicity; multi-document transactions need a
  replica set.
- Neither has `SERIAL`.

Today's `/card/order` handler issues one `UPDATE` per card without a
transaction; two overlapping drags can leave a column with duplicate
positions. A finer-grained interface would carry that bug into every backend.

## Decision

### One method per atomic user action

The `store.Store` interface exposes operations at the granularity of what a
user does, not at the granularity of rows. Each method is atomic within its
backend, and no transaction type leaks through the interface.

```go
package store

var (
    ErrNotFound = errors.New("store: not found")
    ErrConflict = errors.New("store: conflict") // S3 ETag mismatch, Phase 1
)

type Store interface {
    Migrate(ctx context.Context) error
    Ping(ctx context.Context) error
    Close() error

    ListBoards(ctx context.Context) ([]model.Board, error)              // columns + labels, no cards
    GetBoard(ctx context.Context, slug string) (*model.Board, error)   // columns + labels, no cards
    CreateBoard(ctx context.Context, b *model.Board) error             // creates b.Columns too
    UpdateBoard(ctx context.Context, b *model.Board) error             // name/slug only
    DeleteBoard(ctx context.Context, id model.ID) error

    CreateColumn(ctx context.Context, c *model.Column) error           // appended last
    UpdateColumn(ctx context.Context, c *model.Column) error           // name, wip_limit
    DeleteColumn(ctx context.Context, id, moveCardsTo model.ID) error  // moveCardsTo == "" deletes cards
    ReorderColumns(ctx context.Context, boardID model.ID, order []model.ID) error

    ListCards(ctx context.Context, boardID model.ID) ([]model.Card, error) // with labels + subtasks
    GetCard(ctx context.Context, id model.ID) (*model.Card, error)
    CreateCard(ctx context.Context, c *model.Card) error               // appended last in c.ColumnID
    UpdateCard(ctx context.Context, c *model.Card) error               // content; never column/position
    DeleteCard(ctx context.Context, id model.ID) error
    // ReorderCards is the authoritative order of one column. A listed card
    // that currently lives in another column of the same board is moved in.
    ReorderCards(ctx context.Context, boardID, columnID model.ID, order []model.ID) error

    CreateLabel(ctx context.Context, l *model.Label) error
    UpdateLabel(ctx context.Context, l *model.Label) error
    DeleteLabel(ctx context.Context, id model.ID) error
}
```

Everything a page needs is at most two calls (`GetBoard`, `ListCards`), which
is one object read on S3 and two queries on SQL. Business rules (empty title,
WIP limit, slug format) live in `service`, not in backends; a WIP check is a
read followed by a write, and the small race that leaves is acceptable for the
team sizes this project targets.

Export/Import (Phase 1/5) is implemented once in `internal/backup` on top of
this interface rather than once per backend, so every backend produces the
same snapshot by construction. The roadmap's "all backends implement
Export()/Import()" is satisfied through the interface, not by four copies.

### Portable IDs

`model.ID` is a string. IDs are generated by the service with
`crypto/rand.Text()` (Go 1.24, 26 base32 characters, 130 bits) and stored as
`TEXT PRIMARY KEY` in SQL, `_id` in Mongo, and as-is in the S3 JSON.

Alternatives considered:

- Per-backend integer sequences (`SERIAL`, `AUTOINCREMENT`): S3 and Mongo
  would need a counter document, and Export/Import would have to remap every
  reference on the way in.
- UUID v4 strings: equivalent, but 36 characters and needs either a
  dependency or 10 lines of code; `rand.Text` is already there.

### Contract tests

`internal/store/storetest` holds one test suite that takes a `func() Store`
and exercises every method, including reorder edge cases (move into another
column, reorder with an unknown ID, reorder with a duplicate). A backend is
done when it passes the suite. The memory backend exists in Phase 0 so the
suite and the handler tests run without a database.

## Consequences

- Reordering is correct on every backend because it is one operation, and the
  origin column no longer needs a second request.
- IDs change for existing Postgres data during the v1 migration
  ([0002](0002-board-column-card-model.md)). Nothing outside the app holds a
  card ID today, so nothing breaks.
- Adding a backend means implementing ~20 methods and passing one suite; it
  does not mean re-deriving business rules.
- The interface will grow in Phase 3 (users, memberships) and Phase 4
  (personal access tokens). Those are additions, not changes to the methods
  above.
